# Техническая документация — Production Calendar 2026

## 1. Назначение

`production-calendar-2026` — это веб-приложение на Next.js для персонального расчёта зарплаты по производственному календарю 2026 года.

Основные задачи приложения:
- авторизация пользователя через Google;
- хранение индивидуальных настроек расчёта;
- учёт переработок по дням;
- учёт дней отсутствия (`не работал`);
- расчёт месячного и годового итога;
- разбиение выплат на `аванс` и `перерасчёт`;
- экспорт данных в Excel и JPEG.

Приложение не является универсальным payroll-движком. Это специализированный калькулятор под конкретную модель расчёта и конкретный календарный год.

---

## 2. Технологический стек

- **Framework:** Next.js 14.2.35
- **UI:** React 18.3.1
- **Authentication:** NextAuth v5 beta + Google Provider
- **Database:** SQLite через `better-sqlite3`
- **Exports:**
  - `xlsx` — Excel-экспорт
  - `html2canvas` — экспорт визуального представления в JPEG
- **Runtime:** Node.js
- **Production process manager:** PM2
- **Reverse proxy:** nginx

## 6. Аутентификация и доступ

### 6.1. Провайдер

Используется только **Google OAuth** через NextAuth.

Переменные окружения:
- `GOOGLE_CLIENT_ID`
- `GOOGLE_CLIENT_SECRET`
- `AUTH_SECRET`
- `AUTH_URL`
- `AUTH_TRUST_HOST`
- `DATABASE_PATH`

### 6.2. Поток входа

1. Пользователь открывает `/`.
2. `app/page.js` проверяет сессию:
   - если сессия есть → `redirect("/dashboard")`
   - если нет → `redirect("/login")`
3. На `/login` пользователь нажимает кнопку `Войти через Google`.
4. NextAuth запускает OAuth flow.
5. После успешного входа приложение редиректит пользователя на `/dashboard`.

### 6.3. Привязка пользователя в БД

В `auth.js` на `signIn` выполняется upsert:
- если пользователя ещё нет, создаётся запись в `users`;
- для нового пользователя создаётся запись в `settings` со значениями по умолчанию;
- если пользователь уже существует, обновляются `email`, `name`, `avatar`.

Ключ пользователя в приложении — `Google profile.sub`.

### 6.4. Защита маршрутов

`middleware.js` защищает только:
- `/dashboard/:path*`

API-маршруты не защищаются middleware, но каждый API-обработчик отдельно вызывает `auth()` и возвращает `401 Unauthorized`, если пользователь не авторизован.

## 7. Модель данных

SQLite создаётся по пути:
- `process.env.DATABASE_PATH`, если переменная задана,
- иначе `./data/calendar.db`.

Дополнительно:
- включён `journal_mode = WAL`;
- включён `foreign_keys = ON`.

### 7.1. Таблица `users`

```sql
CREATE TABLE IF NOT EXISTS users (
  id TEXT PRIMARY KEY,
  email TEXT UNIQUE,
  name TEXT,
  avatar TEXT,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

Назначение:
- хранение профиля пользователя, полученного из Google.

### 7.2. Таблица `settings`

```sql
CREATE TABLE IF NOT EXISTS settings (
  user_id TEXT PRIMARY KEY REFERENCES users(id),
  oklad REAL DEFAULT 135000,
  ot_rate REAL DEFAULT 164,
  ot_weekday REAL DEFAULT 2,
  ot_saturday REAL DEFAULT 8
);
```

Назначение:
- персональные параметры расчёта зарплаты пользователя.

### 7.3. Таблица `overtime`

```sql
CREATE TABLE IF NOT EXISTS overtime (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT REFERENCES users(id),
  month INTEGER,
  day INTEGER,
  hours REAL,
  UNIQUE(user_id, month, day)
);
```

Назначение:
- хранение часов переработки по дням.

### 7.4. Таблица `absences`

```sql
CREATE TABLE IF NOT EXISTS absences (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT REFERENCES users(id),
  month INTEGER,
  day INTEGER,
  UNIQUE(user_id, month, day)
);
```

Назначение:
- хранение дней, когда пользователь отмечен как `не работал`.

## 8. Календарная модель

### 8.1. Фиксированный год

Приложение жёстко ориентировано на **2026 год**:

```js
const YEAR = 2026;
```

Это влияет на:
- вычисление дней недели;
- праздники;
- сокращённые дни;
- число рабочих дней по месяцам;
- экспортные названия файлов;
- отображение предупреждения, если текущий календарный год отличается от 2026.

### 8.2. Праздники и сокращённые дни

В `app/dashboard/client.js` определены:
- `HOLIDAYS` — множество праздничных дат;
- `PRE_HOLIDAY` — множество сокращённых дней.

### 8.3. Типы дней

Функция `getDayType(month, day)` возвращает один из типов:
- `holiday`
- `preholiday`
- `weekend`
- `workday`

Правила:
1. Если дата входит в `HOLIDAYS` → `holiday`
2. Если дата входит в `PRE_HOLIDAY` → `preholiday`
3. Если день недели — суббота или воскресенье → `weekend`
4. Иначе → `workday`

### 8.4. Нормы рабочих дней по месяцам

`MONTHLY_DATA` содержит жёстко заданные месячные нормы для 2026 года.

Они используются в расчётах зарплаты и вычетов.

## 10. Бизнес-логика расчёта

### 10.1. Общие принципы

Приложение исходит из следующей модели:
- у пользователя есть фиксированный оклад за месяц;
- переработка оплачивается по часовой ставке;
- день `не работал` создаёт долг в **8 часов**;
- этот долг сначала компенсируется переработкой;
- только непокрытый долг уменьшает оклад.

### 10.2. Расчёт показателей месяца

Для каждого месяца считаются:
- `otHours` — суммарные часы переработки;
- `absentCount` — число пропусков;
- `debtHours = absentCount * 8`;
- `effectiveOT = max(0, otHours - debtHours)`;
- `uncoveredHours = max(0, debtHours - otHours)`;
- `deduction = (uncoveredHours / 8) * (oklad / workDays)`;
- `adjustedOklad = oklad - deduction`;
- `otPay = effectiveOT * otRate`;
- `total = adjustedOklad + otPay`.

### 10.3. Важная интерпретация

Это означает:
- если пропуски полностью покрываются накопленной переработкой, оклад не режется;
- если переработки недостаточно, оклад уменьшается пропорционально числу неотработанных дней.

### 10.4. Годовые итоги

Годовая сводка агрегирует:
- эффективные часы переработки;
- оплату переработки;
- суммарные вычеты;
- скорректированный оклад;
- общий итог.

## 11. Логика пропусков (`не работал`)

### 11.1. Поведение при установке пропуска

При отметке дня как `не работал`:
1. день добавляется в `absences`;
2. если на этом дне есть переработка, она удаляется;
3. в БД отправляется обновление для очистки переработки;
4. затем создаётся запись о пропуске.

Таким образом один и тот же день не должен одновременно содержать и переработку, и признак отсутствия.

### 11.2. Где разрешено ставить пропуск

UI позволяет отметить `не работал` только на:
- `workday`
- `preholiday`

На праздниках и выходных такой сценарий не предусмотрен.

## 12. Разбиение на `аванс` и `перерасчёт`

Для текущего месяца приложение дополнительно считает две части выплаты:
- период `1–15`
- период `16–конец месяца`

Логика:
- определяется число рабочих дней в каждом периоде;
- скорректированный оклад делится пропорционально этим рабочим дням;
- переработка суммируется отдельно по каждой половине месяца;
- долг от пропусков распределяется пропорционально рабочим дням каждого периода;
- далее считается сумма `advance` и `settlement`.

В UI это показывается как:
- 💳 карта
- 💵 наличные
- общий итог по половине месяца

## 14. API

Все API-маршруты:
- требуют авторизацию;
- возвращают JSON;
- используют try/catch;
- возвращают `401` для неавторизованного доступа;
- возвращают `400` при невалидных данных;
- возвращают `500` при серверной ошибке.

### 14.1. `GET /api/settings`

Возвращает настройки пользователя.

Пример ответа:

```json
{
  "oklad": 135000,
  "ot_rate": 164,
  "ot_weekday": 2,
  "ot_saturday": 8
}
```

Если запись отсутствует, возвращаются значения по умолчанию.

### 14.2. `POST /api/settings`

Сохраняет настройки пользователя.

Ожидает JSON:

```json
{
  "oklad": 135000,
  "ot_rate": 164,
  "ot_weekday": 2,
  "ot_saturday": 8
}
```

Валидация:
- `oklad`: `0..10_000_000`
- `ot_rate`: `0..100_000`
- `ot_weekday`: `0..24`
- `ot_saturday`: `0..24`

### 14.3. `GET /api/overtime`

Возвращает переработки текущего пользователя в виде объекта:

```json
{
  "0-12": 2,
  "0-13": 2,
  "1-7": 8
}
```

### 14.4. `POST /api/overtime`

#### Single mode

```json
{
  "month": 0,
  "day": 12,
  "hours": 2
}
```

Правила:
- если `hours <= 0`, запись удаляется;
- иначе выполняется insert/update.

#### Bulk mode

```json
{
  "bulk": true,
  "month": 0,
  "items": [
    { "day": 1, "hours": 2 },
    { "day": 2, "hours": 2 }
  ]
}
```

Правила:
- сначала удаляются все переработки пользователя за указанный месяц;
- затем вставляется новый набор значений.

### 14.5. `DELETE /api/overtime?month=<m>`

Удаляет все записи переработки за указанный месяц.

### 14.6. `GET /api/absences`

Возвращает пропуски пользователя:

```json
{
  "0-10": true,
  "0-11": true
}
```

### 14.7. `POST /api/absences`

#### Single mode

```json
{
  "month": 0,
  "day": 10
}
```

#### Bulk mode

```json
{
  "bulk": true,
  "month": 0,
  "items": [
    { "day": 10 },
    { "day": 11 }
  ]
}
```

Bulk-режим заменяет набор пропусков за месяц.

### 14.8. `DELETE /api/absences?month=<m>&day=<d>`

Удаляет пропуск на конкретный день.

### 14.9. `DELETE /api/absences?month=<m>`

Удаляет все пропуски указанного месяца.

- `validateMonth(val)` → `0..11`
- `validateDay(val)` → `1..31`

## 16. Security notes

### Что уже сделано

1. Все API защищены `auth()`.
2. Данные разделены по `session.user.id`.
3. Присутствует валидация входных данных.
4. Добавлены HTTP security headers:
   - `X-DNS-Prefetch-Control`
   - `X-Frame-Options: SAMEORIGIN`
   - `X-Content-Type-Options: nosniff`
   - `Referrer-Policy: strict-origin-when-cross-origin`
   - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
5. `.env.local` исключён из Git.
6. SQLite-файлы исключены из Git.
7. Для аватаров разрешён только `lh3.googleusercontent.com`.

### Ограничения

- Приложение использует локальную SQLite, что подходит для текущего масштаба, но не является HA-решением.
- Годовая логика жёстко зашита и потребует кодовых изменений для 2027+.
- Нет набора автоматических тестов.
- Нет server-side rate limiting.

## 19. Известные ограничения и риски

1. **Жёсткая привязка к 2026 году**
   - Для следующего года нужно обновлять константы, праздники и месячные нормы.

2. **Доменно-специфичная модель расчёта**
   - Пропуск = 8 часов долга.
   - Долг сначала покрывается переработкой.
   - Это не универсальная payroll-модель.

3. **Нет автотестов**
   - Любые изменения формул или календарной модели требуют ручной верификации.

4. **README не отражает полностью текущую эксплуатацию**
   - Историческая команда `pm2 start pm2.config.js` не соответствует текущему репозиторию, так как `pm2.config.js` отсутствует.

5. **SQLite как локальное single-node хранилище**
   - Для текущего сценария подходит, но требует аккуратности при миграциях и бэкапах.

## 21. Краткий итог

`production-calendar-2026` — это продакшн-используемое персональное приложение для расчёта зарплаты и переработок с такими свойствами:
- вход через Google;
- персональные данные на пользователя;
- локальная SQLite-персистентность;
- расчёт оклада, переработки и вычетов;
- учёт пропусков;
- экспорт отчётов;
- развёртывание через PM2 + nginx.

Ключевая особенность проекта: почти вся бизнес-логика сосредоточена в `app/dashboard/client.js`, тогда как серверная часть в основном обеспечивает аутентификацию, валидацию и сохранение данных.
